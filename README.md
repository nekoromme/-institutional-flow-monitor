# 米国株・機関流入候補の検証

機関保有が比較的少ない銘柄の異常出来高を調べ、後の保有報告と照合する研究です。
現在は **対象データの確認を続けながら、第4段階の初回比較まで進めた段階** です。
公開保有報告を使う初回の探索的な比較まで実施しました。実際の機関流入の検出精度や投資成績は未検証です。

**最新結果：優位性を妨げる要因の診断まで実行しました。** 同じ49銘柄でも、反復あり・なしの報告保有増加割合の差は1月末までなら＋28.0ポイント、3月末までなら−3.3ポイントでした。期間を長くまとめる問題に加え、保有集計方法の影響、後の株式併合による補正基準日のずれ、ゼロ出来高の影響を確認しました。条件の最適化はしていません。低保有の主対象は依然2銘柄で、別期間の検証が必要です。[要因診断と次の作業](docs/STAGE4_FACTOR_DIAGNOSTICS.md)へ。

前回はCJMBの61営業日で異常出来高8日、うち反復5日を記録し、同四半期の報告保有株数の減少と対応づけました。[CJMBの試行結果](docs/STAGE3_CJMB_PILOT.md)を参照してください。

**実測：指定5銘柄の市場データ取得に加え、SECの一括保有資料2本・約730万行を走査しました。訂正を反映した集計と発行済み株数の対応を実装しましたが、共同報告などに未解決点があり、機関保有率の認定とバックテストは未完了です。**
原報告4件の全行を照合し、件数不一致による保留2件を根拠付きで修正しました。この5銘柄の原報告の結果は[原報告の確認と修正](docs/STAGE2_REVIEW.md)、以前の集計は[保有資料の初回集計](docs/STAGE2_HOLDINGS.md)にあります。

既定の出来高・反復ルールを2026年1〜3月の5銘柄で実行しました。異常34銘柄日、そのうち反復22銘柄日を記録しましたが、的中率はまだ計算できません。仕様・保留規則・実行結果は[出来高モデルの技術試行](docs/STAGE3_PILOT.md)へ。

2026年初の対象選び用の保有資料も追加しました。確認候補3,181件から最初の200件を固定し、未来の情報を除外する処理を検証しています。[対象選びの現在地](docs/STAGE2_COHORT.md)を参照してください。低保有認定済みの200銘柄という意味ではありません。

固定した200件の原書類を一次点検しました。152件で証券番号と発行会社が一致し、うち137件は当時の銘柄コードまで対応しています。[全候補の点検結果](docs/STAGE2_IDENTITY_FULL.md)に、保留理由と次の対象選定に残る確認事項を記録しました。低機関保有を認定した件数ではありません。

全200件の対象選定表を作り、65件で2025年9月末の保有株数合計と同日の発行済み株数候補が揃いました。100％超となる6件などを確認待ちにし、空欄の機密状態を「あり」とする誤分類も修正しました。[対象選定の材料と修正記録](docs/STAGE2_ELIGIBILITY.md)へ。株式種類・共同報告・当時の上場状況が未確認のため、低機関保有としての採用はまだ0件です。

追加確認ではLSH・KAPA・CJMBの普通株と分母を原書類で照合しました。CJMBは当時の届出による上場記載を代理情報として使う仮定付きで、保有報告を比較する試行の材料が揃っています。LSHの発行契約、KAPAの同じ株数の報告など、残る問題も[普通株・上場記載・共同報告の確認](docs/STAGE2_ADMISSION_REVIEW.md)へ記録しました。低保有判定や検出精度の認定はまだ行っていません。

## 初回の試験

GitHubの `Settings → Secrets and variables → Actions` に、次の二つを登録します。
登録済みなら、やり直す必要はありません。

- `ALPACA_API_KEY`
- `ALPACA_SECRET_KEY`

試験コードが `main` に追加・修正されると試験が起動します。
手動なら `Actions → 第1段階・データ接続試験 → Run workflow` でも実行できます。
結果は該当の実行を開いたときの要約に表示します。
実行成功は市場側の必須試験を通過したことを示します。保有資料の取得状況は別の欄に表示します。

## 何を調べるか

| 試験 | 範囲 |
| --- | --- |
| 市場データ | UAVS・MU・ONTO・AAOI・QMCOの5銘柄。ユーザー指定の試験対象で、低機関保有を確認済みという意味ではありません |
| 日足 | 過去約3年。補正前と株式分割・併合の補正後を比較。追加で2016年のMUの短い期間 |
| 1分足 | 終了から30分以上経過した直近20営業日。通常取引時間と時間外を区別 |
| 歩み値・気配 | 直近終了日の短い1分間。取得件数と時間精度を点検 |
| 配信区分 | 全米市場統合の `sip` を明示指定。単一取引所の `iex` は別の比較試験 |
| 保有報告 | 接続試験はGeode二期。別コマンドで公式一括データの全提出者を走査し、2025年12月末・2026年3月末の指定5銘柄を抽出。全置換の訂正と追加報告を区別 |
| 発行済み株式数 | 日付・公表日を区別して対応。UAVSとQMCOの今回採用する株数を原書類でも照合。現在の保有率としては使わない |

第2段階では、株数の単位を判定日へ補正した過去60営業日の窓を作り、問題のある窓を理由付きで保留します。詳細は[第2段階の仕様](docs/STAGE2.md)を参照してください。

最後のページまで取れたか、データがない区間、不正な値、重複、取得時間、応答容量を記録します。
1分足がないことは、必ずしも通信による欠損とは限らないため、勝手に出来高0で埋めません。

保有報告に銘柄が見つからなくても「機関保有0%」にはしません。
一つの運用会社の報告から、全機関の保有率は計算できません。

## 公開するもの

コードと、接続成否・件数・時刻などの診断情報を公開します。
キー、認証ヘッダー、生の価格・約定・気配はログや添付ファイルに出力しません。
注文を出す処理、口座残高を読む処理、定期監視は含めていません。

標準のPythonだけで動き、追加パッケージのインストールは不要です。
コードの注釈と実行要約は日本語です。

## 開発時の確認

秘密を使わない試験：

```bash
python -m unittest discover -s tests -v
```

登録済みの環境変数を使った接続試験：

```bash
python -m flow_probe
```

キーなしで公的資料だけを調べる場合：

```bash
python -m flow_probe --sec-only
```

公式一括データを取得し、二期の保有資料を点検する場合（APIキー不要）：

```bash
python -m flow_probe.holdings --fetch
```

約190MBのZIP2本と、小さな銘柄一覧・会社提出データを通常の公開経路で取得します。
取得済みなら `--fetch` を省いてローカルの入力だけで再計算できます。
元ファイルのハッシュが今回確認した内容と異なる場合は、黙って上書きせず点検待ちにします。
結果は `diagnostics/holdings/bulk-summary.json`、全監査記録は同じ場所の `bulk-audit.json` と `manager-ledger.json` です。
GitHubの接続試験から、この大きな取得を毎回実行する構成にはしていません。
今回の作業環境では成功しましたが、GitHub実行環境からSECへの403は別途未解決です。

今回の修正に使った原報告4件を、再取得して全行照合する場合：

```bash
python -m flow_probe.filing_review --fetch
```

元の件数の警告は残し、日付・株数・提出番号などが確認した内容と一致する場合にだけ利用判定を追加します。
UAVSのCalamos間の重複は確定できないため、自動で差し引かず、重複の有無による影響を比較結果に表示します。

診断ファイルは `diagnostics/` に作成します。このフォルダはGitの保存対象から除外しています。
GitHubで生成した診断の詳細は、実行ログ内の `STAGE1_DIAGNOSTICS_BEGIN` から `STAGE1_DIAGNOSTICS_END` までにあります。
