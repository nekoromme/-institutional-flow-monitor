# 米国株・機関流入候補の検出と検証ロードマップ

版：0.18／作成日：2026年9月10日

現在地：第4段階の初回比較に続き、期間集約・保有集計・補正差・ゼロ出来高の要因診断まで完了。同じ49銘柄の1月末の反復では報告保有増加割合に＋28.0ポイントの差が出たが、最適化や優位性認定はしていない。主対象は依然2銘柄。SMSI・GAMEの補正基準日のずれを確認し、KAPAの価格差とLSHの0の意味は保留。[要因診断](STAGE4_FACTOR_DIAGNOSTICS.md)。

この計画は、まとまった結果を確認し、ユーザーがときどき方針を修正できるための作業台帳。後から数値・処理・対象を修正できることを、最初から完成条件に含める。

## 1. 目的と、成功の意味

**その時点で公表済みの資料によれば機関保有が比較的少ない米国株について、普段とは異なる出来高とその継続から、機関の保有増加と整合する候補を、後の保有報告より先に見つける。**

目標は固定する。一方、判定方法や数値は検証結果に応じて変更する。

検証する問いは二つに分ける。

| 検証 | 確かめること | 成功と呼ばないもの |
| --- | --- | --- |
| 主目的：機関保有増加との整合性 | 通知した銘柄では、同条件の通知していない銘柄より、後の報告で保有株数の増加が多く観測されるか。単純な出来高急増だけの方法を改善するか | 株価が上がっただけで「機関を検出した」とすること |
| 実用性：投資の調査候補としての価値 | 通知を知ってから取れる行動で、同条件の比較対象より良い値動きが残るか。売買費用や下落リスクに見合うか | 通知前の値上がりを利益に含めること |

機関の保有増加を捉えても、その後に儲かるとは限らない。逆に、値上がりを予測できても、機関が原因とは限らない。両方の成績を別々に示す。

この研究の納品物は、動く監視器に加えて、採用理由、不採用理由、再現できる検証記録。結果が悪ければ「現時点では使わない」という結論も正式な成果にする。

## 2. 前の説明から訂正・保留する点

前に提示された通知例と成績表は、実測結果ではない。提示された範囲では完全な数式・係数・検証記録もないため、計算を再現できない。生成したモデルの種類にかかわらず、すべて未検証の仮説として扱う。

| 前の案 | 問題 | 今回の扱い |
| --- | --- | --- |
| 出来高が平常の3倍 | 銘柄によって普段の変動幅が違う | 自分自身の過去分布でどれほど珍しいかを測る。3倍は採用済みの境界にしない |
| 買いフロー強度が0.35超 | 定義、売買方向の推定方法、未分類取引の扱いが不明 | 初号機から外す。追加する場合は式と誤分類の限界を先に示す |
| 30分以上持続 | 一時的な大口取引との区別には意味があり得るが、30分に根拠がない | まず日ごとの反復で検証。日中の持続は別の追加実験にする |
| 市場超過リターンが+0.5%超 | 出来高の検出と値上がり追随を混ぜる | 初号機の必須条件にしない。市場・業種の影響は比較検証で確認する |
| 当日上昇が+5%未満 | 初動の発見にも誤検出の排除にも効くとは限らない | 最初は記録だけ。採用には追加価値の証拠を求める |
| 過去20営業日を基準 | 短期間の特殊事情に引っ張られる可能性がある | 基準期間は仮説として比較する。長ければ正しいとも考えない |
| 80点・90点なら有望 | 点数と確率・将来利益の対応がない | 初期の総合点を廃止。出来高倍率、珍しさ、反復回数をそのまま示す |
| 勝率が50%なら捨てる | 勝ちと負けの大きさ、市場全体の上昇率を無視している | 平均利益、中央値、費用、下落幅、比較対象との差で評価する |
| 15分遅れはほぼ誤差 | どの時点で利益が消えるかは未検証 | 引け後の方式を先に試し、遅延の価値は後で比較する |
| 数か月記録してから初めて検証 | 利用可能な過去データがあれば、先に仮説を落とせる | 過去検証を前倒し。その後に新しく発生する相場でも確かめる |

例えば、勝率40%でも平均の勝ちが+5%、平均の負けが−2%なら、単純な期待損益は費用前で+0.8%。勝率60%でも勝ち+1%、負け−3%なら−0.6%。これは計算例であり、このモデルの成績ではない。

## 3. できることと、観測できないこと

出来高は売買が成立した株数で、買い手の身元は示さない。買い側・売り側のどちらが積極的に注文したかを推定できても、それだけでは機関か個人か、機関全体が買い越したかは分からない。

答え合わせの中心に使う「Form 13F」は、一定規模の機関投資運用者による四半期末の保有報告。対象証券の運用裁量が1億ドル以上という要件があり、原則として四半期末後45日以内に提出される。したがって毎日の取引履歴にはならない。[米国証券取引委員会の投資家向け説明](https://www.investor.gov/introduction-investing/investing-basics/glossary/form-13f-reports-filed-institutional-investment)

これを踏まえ、通知の名称は「機関流入候補」または「異常出来高候補」とする。「機関が買ったことを確認」とは表示しない。

保有報告には、小口保有の省略、秘密扱い、訂正・追加報告などもある。新しく報告された保有は、本当にその期に初めて買ったとは限らない。[Form 13Fの公式記入要領](https://www.sec.gov/files/form13f.pdf)

**後の13Fは不完全な答え合わせであり、日単位の機関売買の正解表ではない。** 書類で増加が確認できないケースも、直ちに「機関の買いが一切なかった」とは決めない。

## 4. 段階ごとのロードマップ

| 段階 | わたしが作るもの・確かめること | 次へ進める条件 |
| --- | --- | --- |
| 0：目的と検証方針の固定 | このロードマップ、前の案の点検、未検証事項の一覧 | 目的、低コスト優先、少数指標、段階ごとの指示という方針が明文化されている。計画は作成済み |
| 1：データの実現性調査 | Alpaca接続試験、保有報告との銘柄照合試験、取得範囲・欠損・所要時間・保存容量の報告 | 必要な価格・出来高と保有情報が、対象範囲で取得できる。難しい部分と代替案が明確 |
| 2：検証用データと採点ルールの固定 | 当時の銘柄一覧、当時公表済みの保有情報、正解に使う期間、比較対象、期間分割、採否基準 | 未来の情報を混ぜずに再現できる。数値を調整する前に検証方法を記録してある |
| 3：最小モデルの作成 | 出来高の異常度だけの比較用モデルと、反復を追加したモデル。説明可能な判定結果と実行記録 | 同じデータ・設定で同じ結果になる。各数値の意味と通知理由を説明できる |
| 4：過去データでの検証 | 保有増加との整合性、値動き、費用、誤検出、通知量の比較レポート | 良い点と悪い点が分離され、単純な方法より改善したか、不明か、悪化したか判定できる |
| 5：原因を絞った修正 | 旧版と新版の比較、一つずつの変更、採用・棄却記録、触っていない期間での最終確認 | 特定の数値・銘柄・相場だけに依存せず改善が残る。改善がなければ旧版維持・縮小・中止を選べる |
| 6：実際の相場で記録 | 米国市場の引け後に分析・記録・通知。将来の株価と保有報告による継続検証 | 過去検証と実運用の差、停止・欠損、通知の実用性を把握できる |
| 7：継続・拡張・中止の判断 | 本番候補版、変更手順、再検証報告。必要な場合だけ日中分析や追加データの比較 | 費用と手間に対する価値が説明でき、改善が崩れた場合に戻せる |

各段階は一度の会話で終わるとは限らない。長い段階は「1A：価格データ」「1B：保有データ」のように小分けにする。1回の作業では段階をまたいで、次の判断に使える結果までまとめて進める。個別資料の保留で全体を止めず、途中経過を伝えながら、点検・必要な修正・再実行・記録更新を含める。

### 段階1：まずデータが使えるか

最初は、取引の多さが異なる5〜10銘柄程度で接続と品質を試す。これは技術試験用で、投資成績を主張する標本ではない。

Alpacaの公式FAQは、全米市場を統合したデータについて、履歴要求の終了時刻を15分以上前にすれば有料契約なしで照会できると説明している。一方、仮想取引専用アカウントの説明には、IEXという単一取引所のデータに限るとの記述がある。今回発行したキーでどこまで使えるかは実測で確定する。[Alpaca公式FAQ](https://docs.alpaca.markets/us/docs/market-data-faq)、[仮想取引専用アカウントの説明](https://docs.alpaca.markets/us/docs/paper-trading)

試験では次を報告する。

- 全米市場統合の履歴を明示指定して、日単位・1分単位・個々の約定・売買気配を種類別に試す。
- 接続成功だけでなく、取得件数、対象時刻、実際の配信区分、追加ページの取り残し、欠損を確認する。
- 単一取引所のデータへ黙って切り替えない。市場の一部しか測れていない場合は、研究可能な範囲を改めて判断する。
- 403などのエラーだけで「無料では無理」と決めず、認証・要求時刻・権限を分けて調べる。
- 大量取得前に、少量の取得時間と保存容量を測る。全銘柄の歩み値・気配をいきなり集めない。
- 保有報告の証券番号と株式の銘柄コードを照合し、株式の種類、株数、発行済み株式数、訂正報告の扱いを試す。

**この段階の重要な分岐は、安く取得できるかだけでなく、目的を測れるデータかどうか。** 出来高が取れても、過去の保有情報が復元できなければ、機関流入の検証は別途解決が必要になる。

提出データの一括ファイルは米国証券取引委員会が公開している。ただし、収録・更新の時期と個別提出の公表時期は同じではなく、一括ファイルだけで全作業が終わるとは見積もらない。[Form 13F公開データ](https://www.sec.gov/data-research/sec-markets-data/form-13f-data-sets)

### 段階2：対象銘柄と答え合わせの土台

当初は米国上場の普通株を対象にする。上場投資信託、優先株、外国株の預託証券などは、株数と保有情報の意味が異なるため、最初の範囲に混ぜない。

研究対象は、結果を見てから好きな銘柄を選ばず、当時の規則で機械的に選ぶ。最初の本格的な対象数は100〜300銘柄程度を目安とするが、これは処理量の仮置きであり、必要な標本数を満たす保証ではない。

「機関がそれほど入っていない」は、当時公表済みの保有報告から推計する。初期候補は、一定の売買しやすさを満たす対象群の中で、報告保有比率が低い下位3分の1。これも運用上の仮置きであり、優位性がある境界とは扱わない。規模の違いで分類が極端に偏るかも先に点検する。

下位3分の1でも保有比率の絶対水準が高ければ、単に集団内で低いだけ。実際の保有比率と分布を示し、目的に合う低保有銘柄が十分あるかを段階2で判断する。機関保有が少ないことを、割安さや経営の良さとは読み替えない。

保有比率は、同じ種類の普通株について、重複を整理した報告保有株数を対応する発行済み株式数で割る。分母の基準日と公表日を保存し、古さを表示する。分母が不明、対応が曖昧、二重計上の疑いがある場合は「不明」とし、低保有と認定しない。

現在の機関保有率を昔の銘柄選びに使わない。現在残っている銘柄だけのテストは参考検証と明記し、上場廃止・倒産・合併・銘柄変更の履歴を含められるかを調べる。復元できない範囲は除外率と理由を報告し、広い米国株全体へ結論を一般化しない。

時価総額や売買代金の下限・上限は、対象分布とデータ品質を確認してから固定する。前の「500億〜2兆円」は根拠のある採用条件として引き継がない。米国株の研究内では米ドル単位で統一する。

## 5. 最初のモデルは二つの情報から始める

機関保有の少なさは対象選びに使う。最初の検出モデルが使う情報は、次の二つに絞る。

1. **出来高の異常度**：その銘柄の普段と比べて、どれほど多く、どれほど珍しいか。
2. **異常の反復**：単発で終わらず、複数の日に出ているか。

取引が成立した方向の推定は最初から入れない。初号機は買いの確認器ではなく、買いを含む異常売買の候補を出す仕組みとして検証する。

### 数値の意味

表示用の「出来高倍率」は、次の単純な形から始める。

> 当日の出来高 ÷ その銘柄の過去の出来高の中央値

中央値は、大小順に並べた中央の値。大きな出来高の日が少数あっても、普段の基準が引っ張られにくい。

ただし、2倍・3倍という倍率だけでは通知しない。銘柄自身の過去分布と照合し、どれほど珍しいかも確認する。普段から出来高が荒れる銘柄の3倍と、安定している銘柄の3倍を同じ強さにしない。

倍率と珍しさは同じ出来高の見方であり、別々に加点して二重評価しない。

### 未検証の試作仕様

動くものを作るため、出発点を以下のように明示する。**これは採用予定の最適値ではなく、比較される最初の仮説。** 段階2でデータの不足や扱いが分かれば、成績を見る前に修正履歴を付けて変更する。

| 項目 | 出発点 | 変更・検証の扱い |
| --- | --- | --- |
| 計算時点 | 米国市場の通常取引終了後 | 通知の実際の受信可能時刻を別に保存する |
| 出来高の範囲 | 提供元の全米市場の日足出来高 | 第1段階で分足の空白にも約定を確認したため変更。通常時間だけの値とはみなさず一貫して使用。詳細は docs/STAGE2.md |
| 普段の基準 | 直前60回の通常の長さの営業日、当日は含めない | 短縮日を除外。欠けた通常日は飛ばさず窓を保留。感度確認は120営業日など少数に限定する |
| 異常日 | 過去60営業日の出来高分布の95%境界を超える日 | 「上位約5%の珍しい日」という意味。機関の買いである確率95%ではない |
| 反復 | 当日が異常日、かつ直近5営業日に異常日が2日以上 | 過去の各日の判定は、その日より前のデータだけで計算する |
| 総合点 | 作らない | 後に点数化する場合は意味と校正結果を別途示す |
| 判定を見送る条件 | 過去データ不足、未解決の欠損、分母ゼロ、株式分割などの未処理 | ゼロ出来高・異常なしで埋めない |

95%の境界の計算方法、同値の場合、休場日、短縮取引日なども設定と一緒に固定する。短縮取引日を通常日とそのまま比べない。

比較用の最小モデルは「当日が異常日」だけ。反復を入れた版がこれを改善しなければ、複雑化を採用しない。反復は誤検出を減らしても発見を遅らせるため、両方を評価する。

「銘柄ごとに違う」への最初の対応は、銘柄自身の基準で測ること。その後に必要なら売買の活発さなどで少数の群に分ける。最初から銘柄ごとに個別の最適値を探すと、過去の偶然を覚え込む危険が大きい。

## 6. 機関保有増加の答え合わせ

主な結果指標は、当該四半期の**報告保有株数の増減**。価格上昇だけでも増える保有評価額を、流入の中心指標にしない。

株式分割などを揃えた保有株数の増減を、基準となる発行済み株式数で割り、規模の違う銘柄でも比べられるようにする。保有比率だけが上がった場合は、自社株買いなどによる分母の減少を切り分ける。増資・合併に伴う保有変化は、市場での買い集めと区別する。

補助結果として、新たに保有を報告した運用者数、複数運用者への広がりも記録する。ただし、報告の欠落や新規の提出義務発生を、新規買付と決めつけない。

### 時間の取り違えを防ぐ規則

| 時刻・日付 | 使い方 |
| --- | --- |
| 保有の基準日 | いつの保有を報告した書類か。増減の対象期間を決める |
| 書類の公表時刻 | いつからその情報を知り得たか。対象選び・モデル調整に使えるかを決める |
| 市場データの対象時刻 | いつの売買から候補を作ったか |
| データの取得時刻 | 自分たちが実際に受け取れたのはいつか |
| 通知時刻 | ユーザーが行動できた最も早い時刻の基礎 |

例えば7月10日の通知を、6月30日時点の保有が増えていたという8月の報告で「的中」にしない。6月末の保有は、7月10日の売買を説明しないため。この例なら、原則として6月末から9月末の保有変化との整合性を調べる。

7月10日時点の対象選びには、その時点で実際に公表されていた情報だけを使う。後から公表される6月末の保有は、対象選びに遡って投入しない。

四半期内のどの日に買ったかは分からないため、「通知が保有増加期間の中にあり、後の報告と整合した」と評価する。通知後に買われたとまでは断定しない。

「公開より何日早かったか」は、実際の公表日との差として別に示す。運用者別の報告と、集計が十分に揃った時点を区別する。他の公表資料で既に分かっていたケースは、13Fより早かったことと、全公開情報より早かったことを混同しない。

### 訂正・重複・未公表の扱い

提出データには、当初報告、訂正、追加、複数の運用者の関係を示す情報が含まれる。これらを単純合計せず、対応関係を処理する。公式のデータ仕様にも、提出日・報告対象期・訂正種別・証券番号などが定義されている。[公開データの公式仕様](https://www.sec.gov/files/form_13f_readme.pdf)

対象選び用の「当時利用可能な版」と、後日の答え合わせ用の「訂正を反映した版」を分けて残す。公表時刻が分からず日付だけの場合は、保守的に翌営業日以降から利用可能とする。

同じ銘柄の同じ四半期に通知が10回出ても、機関検出の10件の独立した成功にはしない。主な採点単位は銘柄と四半期の組み合わせ。未提出・照合不能・秘密扱いなどで採点できないものは「不明」として件数を示す。

## 7. バックテストの方法と採否基準

### 期間と、先読みの防止

まず取得可能な3〜5年程度を目標に調査し、上昇・下落・落ち着いた相場を含める。保有報告についても複数年・複数四半期を使う。期間の長さだけで有効性は保証されないため、独立した銘柄・四半期・通知事例数と不確かさを示す。

1. 古い期間で仮説を作る。
2. その後の期間で、候補とする設定を比較する。
3. 最後の期間は調整に触らず、一度の最終確認に使う。
4. 過去の時点を順に進める検証では、その時点までに公表され、結果が判明していた情報だけを学習・調整に使う。

ランダムに日付を混ぜて分割しない。値動きの追跡期間が境界をまたぐ事例は分離し、まだ公表されていない保有報告を調整材料にしない。最後の期間を見た後に直したモデルは、その期間を再び「初めて見る試験」と呼べない。新しい将来データで再評価する。

多くの条件を試すほど偶然の好成績を拾いやすい。これは少数の変数でも起こるので、試した設定数と不採用案も保存する。[Baileyほか『バックテストの過剰適合の確率』](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf)

基準期間、異常の境界、反復条件、対象の保有率、売買の出口を一度に総当たりしない。近い設定でも結果が残るかを調べる確認と、最も好成績になる設定を探す作業を区別する。

### 比較相手

- 同時期・同程度の規模・売買の活発さ・保有水準の銘柄から選んだ比較群。
- 異常出来高だけを使う最小モデル。
- 過去に公表された保有増加が続くと考える単純な方法。比較可能な履歴がある場合に使う。
- 値動きでは、市場全体と業種、同条件の株価上昇・下落の影響も確認する。

モデル同士は通知件数や対象の割合を揃えた比較もする。候補を極端に絞った版の的中率だけを見て「改善」としない。通知できた割合、見逃し、発見の遅れも合わせて比べる。

### 成績表に必ず入れるもの

| 軸 | 指標 |
| --- | --- |
| 保有増加との整合性 | 保有株数の増加幅・増加した割合、比較群との差、単純モデルとの差、採点できた件数、不明件数 |
| 発見の実用性 | 通知件数、対象範囲、見逃し、最初の通知日、後の公開との差、反復条件で遅れた日数 |
| 通知後の値動き | 主な観測期間は10営業日。5・20営業日は補助。平均と中央値、市場・業種との差 |
| 売買としての参考値 | 手数料、売買価格差、想定価格とのずれを引いた損益。費用を厳しくした場合の結果 |
| 悪い結果 | 大幅下落した例、保有期間中の最大逆行幅、最悪に近い事例群、上位少数の大当たりへの依存 |
| 安定性 | 年・四半期・売買の活発さ・機関保有水準ごとの結果、設定を少し変えた時の結果 |
| 不確かさ | 銘柄・日付・四半期のまとまりを考慮した推定範囲。データ点をすべて独立と仮定しない |

平均値だけを示して、件数が少ない結果や一部銘柄への集中を隠さない。保有増加の基準を二択にする場合、その境界も結果を見る前に決め、連続した増減幅を併記する。

### 通知後の価格から評価する

引け後に通知する方式では、当日の終値で既に買えたことにしない。原則として、通知を受け取った後の次の通常取引開始時を購入の基準にし、買えない場合は未成立として扱う。

基準となる10営業日の定義、出口の時刻、売買費用を固定する。5日、10日、20日のうち一番良かったものだけを後から主結果にしない。

通知が重なった場合は、同一銘柄への重複した仮想購入を管理する。通知単位の値動きは戦略全体の運用成績と分け、実際の資金を想定する場合には同時保有数・投入額・保有期間を決めた検証を別途行う。

### 採用・保留・棄却

| 判定 | 条件と行動 |
| --- | --- |
| 次の検証に採用 | 当初の主目的で比較相手への改善があり、不確かさと対象数を踏まえて検証を続ける価値がある。最終的な有用性とは言い切らない |
| 本番候補 | 調整に使っていない期間と、その後の実際の相場でも改善が残る。通知量、品質、費用に実用性がある |
| 保留 | 事例不足、資料不足、推定範囲が広い。都合よく境界を下げず、データ追加または対象縮小で解決する |
| 修正 | 誤検出や取り逃しの原因が特定でき、目標に沿った少数の修正で比較できる |
| 棄却・中止 | 単純な方法との差がない、触っていない期間で消える、機関との整合性がない、費用やデータ不足で目的を満たせない |

実用上どれほどの改善幅なら続けるか、どれほどの通知量なら使えるかは、段階2の検証計画で事前固定する。数値は標本数・費用・通知量の実測から提案する。根拠なしに「勝率60%なら合格」のような数字を現在の段階で決めない。

保有増加との整合性だけが良い場合は、機関の調査候補抽出器として継続を検討する。値動きだけが良い場合は、機関流入検出としての成功とは扱わず、目的を変更するかユーザーに判断してもらう。

## 8. 修正しても検証が壊れない作り

最初から処理を、データ取得、整形、対象選び、指標計算、判定、検証、通知に分ける。取得先や通知条件の変更で、過去の成績が黙って書き換わらないようにする。

| 保存する情報 | 目的 |
| --- | --- |
| 元データ・取得元・取得時刻・配信区分 | 後日の再計算、配信変更や欠損の調査 |
| 対象銘柄一覧と採用・除外理由 | 当時の対象選びを再現する |
| データの版・モデルの版・設定値・プログラムの変更番号 | どの組み合わせで出た結果かを特定する |
| 判定対象の全記録 | 通知した銘柄だけでなく、通知しなかったもの・欠損で判定できなかったものも比較する |
| 最初の通知と通知後の再計算 | 実際に知れたことと、後から訂正されたことを区別する |
| 実験台帳 | 仮説、変更点、比較期間、費用、成績、採否、不採用理由を残す |
| 実行記録・エラー・復旧状況 | 初心者のユーザーに原因の調査をさせず、わたしが切り分ける |

変更は原則一つずつ。例えば「日中の反復を追加」と「株価条件を追加」を同時に行わない。旧版を残して同じ条件で比較し、改善が確認できたものだけを本番候補へ移す。

小さな数値変更でも通知対象が変わるならモデル変更として記録する。表示文の誤字や、通知対象を変えない不具合修正とは区別する。

意味のある確認として、未来の情報が混入しないこと、株式分割・欠損・訂正を誤処理しないこと、再実行で重複しないこと、秘密情報がログに出ないことを検証する。

## 9. 実際の相場での運用と、拡張の順序

最初は引け後の分析を基本にする。過去検証の後、実際に新しく発生するデータで、記録・仮の売買評価・通知を試す。自動売買をこの計画の完成条件には含めない。

通知がない日にも、正常に調べて候補0件だったのか、未実行・欠損だったのかが分かる実行報告を残す。取得失敗時の再試行、途中からの再開、二重通知の防止、所定時刻まで実行されなかったことの検知を設計する。

1〜3か月の観測は、動作・通知量・短期の値動きを確認する初期区間。機関保有との答え合わせは四半期の終了と公開を待つため、より長くなる。数か月動いたことをもって、有効性の証明とはしない。

見直しの提案時期は、運用不具合を随時、短期の値動きを月ごと、保有増加との整合性を四半期報告が揃った後とする。これは今後の運用設計であり、この会話で定期実行を設定したという意味ではない。モデルの更新は結果を提示してからユーザーの指示に合わせて行う。

追加機能は、下の順序で必要性を判断する。全段階を必ず実装する計画にはしない。

| 優先 | 追加候補 | 採用を考える理由 |
| --- | --- | --- |
| 1 | 決算・増資・指数入れ替え・株式分割などの事実表示 | 誤検出の原因を説明する。最初からすべての材料日を除外せず、材料あり・なしを比較する |
| 2 | 1分データからの日中の異常分布・持続 | 終了間際の一括取引など、一時的な出来高への依存を切り分ける |
| 3 | 約定と気配からの売買方向推定 | 売り主導の候補が多く、方向推定に追加価値がありそうな場合 |
| 4 | 15〜30分遅れの日中通知 | 引け後には優位性が失われることが確認された場合 |
| 5 | 有料のリアルタイムデータ・より細かい板情報 | 追加費用を上回る改善が検証で見込める場合 |

約定と気配の推定では、判定できない取引を無理に買い・売りへ振り分けない。成立後に出た気配を使う先読み、古い気配、気配の中間値での成立を管理する。大きな取引をそのまま機関と決めるルールは採用しない。

ニュース検索で情報が見つからない場合は「確認した範囲では見つからない」と表示する。「公開材料なし」を確定事実にして加点しない。

機械学習は必須の終着点にしない。少数の指標で価値が出ればそこで止める。生成AIは当面、設計・調査・説明・障害調査に使い、銘柄ごとの点数を毎回自由に作らせる方式にはしない。

## 10. 公開リポジトリと費用の方針

GitHubのリポジトリは、ユーザーが選んだ公開設定を前提に進める。コード、説明、検証方法を公開できる構成にする。

Alpacaの秘密設定は `ALPACA_API_KEY` と `ALPACA_SECRET_KEY`。ユーザーが秘密設定欄に登録し、チャットやコードに貼らない。通知用の秘密URLも同様に扱う。

**公開リポジトリでは、取得した市場データを実行ログや添付成果物へ置けば非公開になる、とは考えない。** GitHubのログや実行成果物には、リポジトリの読み取り権限を持つ利用者が閲覧・取得できるものがある。[実行ログの公式説明](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs)、[実行成果物の取得条件](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

このため、データの利用・保存・再配布条件を確認し、生データと秘密情報は公開対象から外した保存先を設計する。公開する診断結果は、接続の成否、件数、所要時間など必要な情報に絞る。データ保存先・保持期間・消失時の復旧は段階1〜2で決める。

市場データ代は無料から始める。ただし、無料の取得と、長期間の保存・大量処理が無料で済むことは別。固定費のある契約を前提にせず、少量試験から実際の負荷を見積もる。

GitHubの自動実行を使う場合も、定刻に必ず動く前提にしない。遅れや欠落を検出し、後から未処理期間を取得できるようにする。公開リポジトリでは活動がない状態が続くと定期実行が停止する仕様にも対応する。[GitHubの定期実行の説明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

初期費用の見積もりでは、価格データ、保有データの整備、保存容量、処理時間を分ける。必要な課金が判明した時点で、価格・必要性・代替案を提示し、契約する前にユーザーが選べるようにする。

| --- | --- |

毎回の引き継ぎは、次の五点に揃える。

1. 今回どこまで終わったか。
2. 何が分かったか。実測と仮説を分ける。
3. 何を変更したか、または変更しなかったか。
4. 未解決の問題と、次の最小作業。
5. ユーザーに必要な操作があれば、その操作だけ。

ユーザーが数式やエラーログを自力で解読することを、次へ進む条件にしない。結果に使った数字の意味と、なぜその変更が必要かはわたしが説明する。
